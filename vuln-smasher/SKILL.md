# vuln-smasher

## When To Use

This skill is used when a user wants to remedy one or more security
vulnerabilities in a given repository.

## Instructions

1. Identify all dependency ecosystems used in the current repository (e.g. npm,
   go, pip, docker, java, cargo).
2. Query available security alerts for the current repository, if security
   alerts are available (e.g. Dependabot alerts, Vanta scans, GHSA alerts).
3. Use ecosystem tools to detect vulnerabilities directly (e.g. `pnpm audit`).
4. Present detected vulnerabilities to the user for review. Organize by
   severity.
5. Ask the user how they would like to proceed, offering several choices.
6. If the user wants to proceed, patch the vulnerabilities. Adhere to the
   guidance in this skill.
7. Use one commit per dependency patched, unless otherwise specified.

## Parameters

This skill may be invoked with particular parameters. Here's what is expected
given the parameters provided at runtime:

- When one or more dependency names are provided...
  - Identify those dependencies in the current project
  - Look up security vulnerabilities affecting those dependencies
    - Use the ecosystem-appropriate tooling for analyzing each dependency
    - Include GHSA or CVE lookups
- When a vulnerability ID is provided (e.g. a CVE or GHSA ID)...
  - Identify the affected dependencies in the current project
- When no parameters are provided...
  - Identify known ecosystems in the current project
  - Query the relevant ecosystem tools for security vulnerabilities

## Severity

Unless specified by a user, assume a default minimum severity level of `high`
(on a scale of `low`, `moderate`, `high`, `critical`) in whichever ecosystem is
being examined (the terms may differ per ecosystem).

If no vulnerabilities are detected at or above the given severity level, ask the
user if they would like to widen the search to include vulnerabilities at less
severe levels.

## Transitive Dependency Remediation

If manifest and lockfile constraints are already wide enough to permit the
patched dependency, perform a lockfile update (e.g.
`pnpm audit --fix update <package>`).

If constraints are not wide enough for a lockfile update, consider the following
strategies:

- Upgrading an ancestor of the affected dependency, if such an upgrade results
  in either the patching or removal of the affected dependency.
- Adding an override (e.g. `pnpm-workspace.yaml` overrides) to force the
  transitive dependency to a patched version.

## Important Constraints

Never directly write modifications to lock files that are generated by other
tools (e.g. `pnpm-lock.yaml`, `package-lock.json`, `uv.lock`, `go.sum`).
Instead, invoke the appropriate tool responsible for those files (e.g. `pnpm`,
`npm`, `go`). It _is_ okay to modify manifest files (e.g. `package.json`,
`pnpm-workspace.yaml`, `go.mod`).

When remediating a dependency that uses semver (semantic versioning), prefer
patches within the current major version.

Overrides that bump a package version past its current major should be avoided.
If unavoidable, major version overrides should be validated by determine how the
dependency in question is used in its dependent packages.

Treat overrides as a short-term solution. As soon as it is feasible to perform a
regular upgrade of the affected dependency or its ancestors, overrides should be
removed and those dependencies upgraded instead.

Keep track of the reasons for overrides. If a record of override reasons is not
already established, suggest use of a human and machine-readable format such as
a YAML or TOML file containing overrides, their reasons, and other useful
metadata that could help inform when an override could be removed in the future.
Prefer linking to GHSAs or CVEs instead of duplicating vulnerability
descriptions inline.
