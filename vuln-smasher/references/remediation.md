# Remediation

## Transitive Dependency Remediation

If manifest and lockfile constraints are already wide enough to permit the
patched dependency, perform a lockfile update (e.g.
`pnpm audit --fix update <package>`).

If constraints are not wide enough for a lockfile update, consider the following
strategies:

- Upgrading an ancestor of the affected dependency, if such an upgrade results
  in either the patching or removal of the affected dependency.
- Adding an override (e.g. `pnpm-workspace.yaml` overrides) to force the
  transitive dependency to a patched version.

## Important Constraints

Never directly write modifications to lock files that are generated by other
tools (e.g. `pnpm-lock.yaml`, `package-lock.json`, `uv.lock`, `go.sum`).
Instead, invoke the appropriate tool responsible for those files (e.g. `pnpm`,
`npm`, `go`). It _is_ okay to modify manifest files (e.g. `package.json`,
`pnpm-workspace.yaml`, `go.mod`).

When remediating a dependency that uses semver (semantic versioning), prefer
patches within the current major version.

Overrides that bump a package version past its current major should be avoided.
If unavoidable, major version overrides should be validated by determine how the
dependency in question is used in its dependent packages.

Treat overrides as a short-term solution. As soon as it is feasible to perform a
regular upgrade of the affected dependency or its ancestors, overrides should be
removed and those dependencies upgraded instead.

Keep track of the reasons for overrides. If a record of override reasons is not
already established, suggest use of a human and machine-readable format such as
a YAML or TOML file containing overrides, their reasons, and other useful
metadata that could help inform when an override could be removed in the future.
Prefer linking to GHSAs or CVEs instead of duplicating vulnerability
descriptions inline.
